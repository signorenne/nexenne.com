#+TITLE: Content Pipeline

This file owns authored content loading and parsing. File placement rules live
in [[file:file-system.org][File system layout]].

The writing lives outside the app. The app reads it at build time and turns it
into static pages.

* Source Folders

- =content/blog/= blog posts in Markdown or Org mode
- =content/work/= work case studies in Markdown or Org mode
- =content/resume/= resume source content

* Blog And Work Loaders

=src/lib/content/blog.server.ts= and =src/lib/content/work.server.ts= use
=import.meta.glob= with =eager: true= to load content at build time.

Each file is:

1. Parsed by =parseByPath=.
2. Validated with a Zod schema.
3. Grouped by slug into a bilingual bundle. A bundle holds a =byLang= map (the
   English and Italian versions) and a =source= fallback, so a page can show the
   requested language and fall back when a translation is missing.
4. Returned to route loaders as full content or as lighter metadata.

Work bundles are sorted newest first using =src/lib/content/recency.ts=, which
turns a free-text date into a sortable number. Drafts show in development and are
skipped in production.

* Covers

A blog post declares =image= and a case study declares =cover=. Both are
root-relative paths under =static/=, and both routes prefix the SvelteKit base
path when rendering, so never write the base path into the content.

- The work index card and the case-study header are both built around the cover.
  =src/lib/content/work.server.test.ts= fails when a project has none, when the
  two translations disagree, or when the path does not resolve to a real file.
- Keep both language versions of a project on the same image. It is the same
  work, and a language switch that changes the picture reads as a different page.
- Product photography lives at =static/work/<slug>/product.webp=. When a project
  has none, point =cover= at the most representative asset it does have, such as
  a screenshot or an architecture diagram.
- In Org files the keyword is =#+COVER:=, matching the other frontmatter
  keywords in that format.
- =cover_fit= chooses how the image fills its frame, and defaults to =cover=.
  The narrowest frame a cover is drawn in is the index card, at roughly 3:1, so
  landscape photography crops well but anything portrait, square, or vector does
  not: a 1080x2280 screenshot cropped to that frame shows 16% of itself. Set
  =cover_fit: contain= for those and the image is matted on the project's accent
  instead. The test reads the real pixel dimensions and fails on a cover that
  would be cropped to a sliver, so this is enforced rather than remembered.

* Spotlight

The home page shows curated projects, not simply the most recent ones. A case
study opts in with =spotlight: true= (=#\+SPOTLIGHT:= in Org), and
=getSpotlightWorkMeta= returns them newest first. With nothing flagged it falls
back to recent work, so the section is never empty because frontmatter is
missing.

Flag both language versions of a project together. The layout in
=.bento--spotlight= is sized for the current count: the card shapes are picked so
they tile a four-column and a two-column grid without leaving holes. Adding or
removing a project changes that, so re-derive the spans rather than assuming the
old ones still fit.

* Parser

=src/lib/content/parser.server.ts= handles both formats:

- Markdown: =gray-matter=, =remark-parse=, =remark-gfm=, =remark-rehype=
- Org: =uniorg-parse= and =uniorg-rehype=
- Code highlighting: =rehype-highlight=
- HTML output: =rehype-stringify=

It also builds the table of contents from headings, adds code-line wrappers,
and fixes internal links/images when a =BASE_PATH= is used.

* PlantUML Diagrams

Architecture, state, activity, class, and sequence diagrams use PlantUML rather
than text-based ASCII art.

- Keep the editable =.puml= source beside its rendered =.svg=.
- Blog diagram pairs live under =static/blog/images/<slug>/=.
- Work case-study diagram pairs live under
  =static/work/<slug>/diagrams/=.
- Reference the =.svg= from authored content. Do not reference the =.puml=
  directly.
- Follow each diagram with a short, visible caption that explains the
  relationship or behavior it shows. Keep accessibility text on Markdown
  images as well.
- Use PlantUML's default visual style unless a documented design requirement
  calls for a different theme.
- Reuse one diagram asset from both language versions when the diagram has
  shared labels and meaning.

Generate or refresh an SVG with:

#+begin_src sh
plantuml -charset UTF-8 -checkonly path/to/diagram.puml
plantuml -charset UTF-8 -tsvg path/to/diagram.puml
#+end_src

Both commands must succeed before the content build. Commit the source and the
rendered SVG together because the static site does not generate PlantUML during
the SvelteKit build.
